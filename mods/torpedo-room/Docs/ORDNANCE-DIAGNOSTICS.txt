This test correction retains the native request selected through our Manage Ordnance button while the old station releases. It requires 0.5 seconds of continuous stable FPP camera/interaction state and stops waiting after 8 seconds. Native save protection briefly blocks saving during this handoff to avoid saving a partly dispatched carry order. It releases on dispatch, abort or world reset. Character/task/view changes abort instead of forcing the order through. No new crew eligibility is granted. No task animation is fabricated; the original native action is submitted once after release.

At 1x, use a fresh start from the same save for each attempt, quick-swapping from a scope or TDC:
1. Our Manage Ordnance -> Load only.
2. Our Manage Ordnance -> Load and maintain.
3. Our Manage Ordnance -> maintenance of an already loaded torpedo, using an engineer.
Leave controls untouched after confirmation. If it fails, wait 15 seconds; do not walk over or retry to rescue the task. Report attempt order and actor, and send this session's output_log.txt before restarting again. We already have manual success comparisons. A fourth test through the tube's own small inventory is optional; that unbound global-queue path is not corrected here.

Search [TorpedoRoom][ORD-DIAG] for DEFER request, camera changes, settled submission or abort reason, plus native action start/stop. Each inventory open has a 90-second/300-line window and at most twice-per-second state samples. Up to six camera caller stacks are logged per session. Async StartAction RETURN is only return of its task, not task completion. Logs contain crew names/positions and may contain local stack paths; the mod does not upload them.

The correction is compiled/offline tested but not live tested. Native global inventory empty tasks, right-click behavior, prior exit crash, physical aft door/flood mismatch and layout at every UI scale are unresolved. No torpedo physics, dud logic, launch depth, configuration migration or TRC9 changes.
